# Linkud 개인 프로젝트 기획서

작성 2026-10-26 · 이정우 · 원본(그림 포함): https://claude.ai/artifact/33VyZURZazAw92VtYaAxfJ

## 1. 개요

Linkud는 AI 에이전트와 MCP 서버 사이에 서서, 도구를 에이전트에게 보여주기 전에 검증하고 신뢰 등급에 따라 전체 허용·읽기만·차단을 자동으로 정하는 게이트웨이다. 링커슈 팀 확정 주제 「MCP 도구 설명 프롬프트 인젝션 탐지 기반 신뢰도-권한 자동 매핑 게이트웨이」를 개인 프로젝트로 구현한다. 산출물은 GitHub 레포(fapp1004-prog/Linkud)와 실제 배포된 서비스다.

**해결할 문제.** 에이전트는 `tools/list`로 받은 도구 이름·설명·입력 형식을 그대로 LLM 프롬프트에 넣는다. 설명에 악성 지시를 숨기면(툴 포이즈닝) 실행 전에 이미 공격이 성립하고, 모델 자체 안전장치로는 막기 어렵다(MCPTox 평균 공격 성공률 36.5%, 최고 72.8%). 승인 후 설명을 몰래 바꾸는 러그풀은 사람의 1회 검토도 우회한다.

**출발점이 된 진단.** 유연호 교수님(Q2)은 이를 "기존 워크로드 신원·권한 문제에 에이전트의 자율성이 더해진 확장 문제"로 보았고(Q6), 워크로드 신원만으로는 도구 설명·기능을 신뢰할 수 없으니 도구 수준 검증 계층이 필요하다고 했다. Linkud가 그 계층이다.

## 2. 목표와 범위

목표는 팀 설계의 파이프라인(탐지 → 신뢰도 산정 → 권한 결정 → 실행 통제)을 실제로 돌아가는 서비스로 만들고, 탐지 성능과 지연 오버헤드를 수치로 보여주는 것이다. 핵심을 먼저 끝내고 확장을 붙인다.

| 구분 | 포함 내용 |
| --- | --- |
| 핵심 | 투명 프록시, 도구 정의 해시·등급 캐시, 러그풀 감지, 규칙 필터, LLM 판별, 결정 테이블, 등급별 권한 매핑(전체 허용 / 읽기만 / 차단), 감사 로그 |
| 핵심 | 공급망 검증: Registry `server.json` → 패키지 → SBOM 생성 → OSV 조회, annotations 불일치 탐지 |
| 핵심 | 배포: EC2, nginx(TLS), 게이트웨이 인증, 비밀값 관리, CI/CD |
| 확장 | 승인 대기 처리: 관리 API + Slack 승인 버튼 |
| 확장 | 인자 검사: 허용된 도구라도 위험한 값(`~/.ssh` 경로 등)으로 호출하면 차단 |
| 범위 밖 | 도구 실행 결과(응답) 안에 숨은 인젝션, SPIFFE/mTLS 등 NHI 인프라, 원격 서버 소스코드 악성 분석, stdio 서버 실행 |

## 3. 전체 아키텍처

게이트웨이는 에이전트 쪽에서는 MCP 서버 하나로 보이고, 뒷단 MCP 서버들에는 클라이언트로 붙는다. 모든 `tools/list`와 `tools/call`이 집행 계층을 지나기 때문에 그 사이에 검사를 끼울 수 있다.

구성요소 (원본 문서에 그림 있음):
- 에이전트(Claude 등) ⇄ HTTPS ⇄ **집행 계층** — 목록 필터(등급에 따라 도구를 보여주거나 숨김), 호출 가드(캐시된 등급만 조회, LLM 없음) ⇄ MCP 서버들(원격 HTTP만 등록)
- **검증 엔진** — 새 도구·해시 변경 시: 규칙 필터 → LLM 판별 → 공급망 조회 → 결정 테이블 → 등급 저장. 외부로 LLM API, Registry·OSV 호출
- **저장소** — 캐시(해시 → 판정), DB(판정 이력·승인·로그)
- **관리 API** — 승인 대기 처리, 감사 로그 조회, Slack 알림(확장). 관리자가 애매한 도구를 승인
- 전체가 EC2 위 Docker Compose로 동작

무거운 검증과 가벼운 조회를 나눈 것이 교수님 Q7·Q8 원칙의 구현이다.

## 4. 판정 파이프라인

경로는 둘이다. 매 요청 도는 런타임 경로는 해시와 캐시만 보고, 무거운 검증 경로는 캐시에 없는 도구가 나타났을 때만 돈다. 검증은 요청이 온 그 자리에서 동기로 하고(결정 1), 승인 대기 도구는 승인 전까지 숨긴다(결정 2).

- **런타임 · tools/list (매 요청):** 요청 도착 → 다운스트림 목록 받기 → 도구 정의 정규화·해시 → 캐시에 있나? → 있음: 등급별 필터 → 에이전트 응답
- **검증 경로 (없음: 새 도구이거나 해시가 바뀜):** 규칙 필터(패턴 검사) → LLM 판별(MCPTox 3요소) → 공급망 조회(SBOM·OSV) → 결정 테이블(4개 등급 중 하나) → 캐시·DB 저장 → 등급 확정 후 등급별 필터로. 검증 실패·타임아웃이면 그 도구는 숨김(fail-closed)
- **런타임 · tools/call (매 요청):** 요청 도착 → 등급 조회(캐시만, LLM 없음) → 허용된 도구? → 예: 다운스트림 호출 전달 / 아니오: 거부·로그 기록

러그풀 감지는 따로 장치가 없다. 승인된 도구의 설명이 한 글자라도 바뀌면 해시가 달라져 캐시 미스가 나고 자동으로 검증 경로를 다시 탄다. 같은 새 도구에 동시 요청이 와도 검증은 한 번만 돌도록 락을 건다.

## 5. 신뢰 등급과 권한 매핑

등급은 서버 단위로 매기고, 권한은 그 등급에 따라 도구 단위로 걸러서 주는 방식으로 집행한다. MCP에는 권한 설정이 따로 없으므로, 게이트웨이가 어떤 도구를 보여주고 실행시킬지 고르는 것이 곧 권한이다.

| 등급 | 권한 | 에이전트에게 보이는 도구 | 호출 시 |
| --- | --- | --- | --- |
| 신뢰 | 전체 허용 | 전부 | 통과 |
| 부분신뢰 | 읽기만 | 읽기 도구만 | 읽기 도구만 통과 |
| 불신 | 차단 | 없음 | 거부 |
| 승인 대기 | 미정 | 없음(숨김) | 거부, 사람이 위 셋 중 하나로 확정 |

**서버 등급 = 가장 위험한 도구 기준.** 도구 하나라도 악성이면 서버 전체를 차단한다.

**읽기 도구 판별.** 아래 세 신호가 모두 "읽기"일 때만 읽기로 인정하고, 하나라도 애매하면 쓰기로 취급한다.
1. annotations의 `readOnlyHint` (서버의 자기 신고, 단독으로는 믿지 않음)
2. 이름 패턴 (`get_`, `list_`, `read_` 대 `create_`, `delete_`, `write_`)
3. LLM 판별 시 "이 도구가 쓰기·삭제를 하는가"를 함께 질문

**결정 테이블 초안.** 점수 합산 대신 위에서부터 차례로 검사해 처음 맞는 줄의 등급을 준다.

| 순서 | 조건 (도구 단위) | 판정 |
| --- | --- | --- |
| 1 | LLM "악성" 고확신, 또는 규칙 필터 치명 패턴(숨은 지시 + 민감 경로), 또는 OSV 악성 패키지(`MAL-`) | 불신 |
| 2 | LLM "의심", 또는 규칙 필터 일반 패턴, 또는 annotations 불일치 | 승인 대기 |
| 3 | Critical·High CVE, 또는 공급망 정보 없음 | 부분신뢰 |
| 4 | 위 어느 것에도 해당 없음 | 신뢰 |

가중치·임계값은 평가 단계에서 오탐률을 보며 정한다.

## 6. 공급망 검증

MCP 서버에는 SBOM 파일이 없지만, 공개된 메타데이터를 따라가면 패키지를 찾아 SBOM을 직접 만들 수 있다.

1. **Registry 조회:** MCP 공식 Registry의 `server.json`에서 소스 레포(`repository`), 배포 패키지(`packages`: npm·PyPI·OCI 이미지 이름과 버전), 원격 주소(`remotes`)를 읽는다.
2. **서버 매칭:** 등록된 원격 주소가 `remotes`와 일치하는지 확인해, 이 서버가 어떤 패키지 몇 버전인지 연결한다.
3. **SBOM 생성:** 패키지를 내려받아(실행하지 않음) syft 등으로 의존성 목록을 만든다.
4. **OSV 조회:** 의존성마다 알려진 취약점(CVE)과 악성 패키지 기록(`MAL-`)을 조회한다.
5. **annotations 불일치:** "읽기 전용"이라고 신고했는데 설명·이름이 쓰기·삭제를 말하면 의심 신호로 남긴다.

결과는 `패키지@버전` 단위로 캐시한다. Registry에 없는 비공개 원격 서버는 "공급망 정보 없음"으로 기록한다.

## 7. 기술 스택과 배포 구조

| 영역 | 선택 | 역할 |
| --- | --- | --- |
| 언어·SDK | Python 3.12, MCP Python SDK 2.x | 게이트웨이 서버면·클라이언트면 |
| 통신 | Streamable HTTP (로컬용 stdio) | 에이전트가 URL로 접속 |
| 캐시 | Redis (검토 중: 파이썬 메모리 캐시로 축소) | 해시 → 판정, 검증 중복 방지 락 |
| DB | PostgreSQL (검토 중: SQLite로 축소) | 서버·도구·판정 이력, 승인 대기열, 감사 로그 |
| LLM | 미정 | 도구 설명 판별 |
| 공급망 | MCP Registry API, syft, OSV API | SBOM 생성·취약점 조회 |
| 서버 | AWS EC2 (t3.small 급) | 전체 서비스 실행 |
| 앞단 | nginx + Let's Encrypt | TLS, 레이트 리밋, SSE 위해 버퍼링 끔 |
| 인증 | 게이트웨이 접속 토큰(추후 OAuth) | 공개 엔드포인트 보호 |
| 비밀값 | AWS SSM Parameter Store 또는 Secrets Manager | LLM API 키 등 |
| CI/CD | GitHub Actions | 테스트 → 이미지 빌드 → EC2 배포 |

뒷단 MCP 서버는 원격 HTTP 서버만 등록받는다. 게이트웨이 장애 시에는 fail-closed(차단)로 동작한다. RDS는 쓰지 않는다(DB는 EC2 내부 컨테이너 또는 SQLite 파일).

## 8. 평가 계획

평가는 "얼마나 잘 잡는가"와 "얼마나 느려지는가" 두 축으로 한다. 실험 전 수치는 확정하지 않고 측정 후 README에 공개한다.

| 축 | 데이터 | 지표 |
| --- | --- | --- |
| 탐지 | 악성: MCPTox 케이스(라이선스 확인 후), 직접 만든 오염 서버 / 정상: MCP 공식 레퍼런스 서버 | 탐지율, 오탐률, 미탐률 (규칙만 / LLM만 / 둘 다 비교) |
| 러그풀 | 승인 후 설명을 바꾸는 테스트 서버 | 변경 감지율, 변경 후 노출까지 걸린 요청 수 |
| 권한 | 읽기·쓰기 도구가 섞인 서버 | 읽기 판별 정확도, 부분신뢰에서 쓰기 도구 노출 0건 여부 |
| 지연 | 가상 호출 부하(k6 또는 Locust) | 게이트웨이 없음 / 캐시 히트 / 첫 검증의 지연·처리량 |
| 판별기 내성 | 판별 LLM을 노리는 공격 샘플 | 오판 유도 성공률 |

MCPTox 기준선(평균 36.5%, 최고 72.8%)은 게이트웨이 적용 전후 비교의 기준으로 쓴다.

## 9. 개발 단계와 일정

핵심 기능과 배포까지 8주, 확장은 그 뒤. 각 단계는 돌아가는 상태로 끝낸다. 마감일이 정해지면 날짜로 바꾼다.

| 주차 | 단계 | 완료 기준 |
| --- | --- | --- |
| 1 | 투명 프록시 | 에이전트가 게이트웨이 하나로 여러 MCP 서버의 도구를 보고 호출할 수 있다 |
| 2 | 해시·캐시·러그풀 | 도구 설명을 바꾸면 게이트웨이가 변경을 감지해 그 도구를 숨긴다 |
| 3~4 | 규칙 필터·LLM 판별 | 오염된 설명을 넣으면 판정과 근거가 나온다 |
| 5 | 결정 테이블·권한 매핑 | 서버마다 등급이 매겨지고, 부분신뢰 서버는 읽기 도구만 보인다 |
| 6 | 공급망 검증 | Registry에 있는 서버의 SBOM을 만들고 OSV 결과가 등급에 반영된다 |
| 7 | 테스트 서버·평가 | 8장의 지표가 표로 나온다 |
| 8 | 배포 | 공개 URL에 HTTPS·인증을 건 게이트웨이가 돌고, push하면 자동 배포된다 |
| 9~ | 확장 | 관리 API·Slack으로 승인하고, 인자 검사로 위험한 호출을 막는다 |

## 10. 리스크, 미결 사항, 팀 설계와 다른 점

가장 큰 한계는 도구 응답 안에 숨은 인젝션을 못 잡는다는 점이고, 팀 보고서와 같이 범위 밖으로 명시한다.

**리스크**

| 리스크 | 완화 방법 |
| --- | --- |
| LLM 판별기 자체를 우회하는 공격 | 규칙·공급망·annotations 신호와 결합, 애매하면 사람 승인 |
| 오탐으로 정상 도구 차단 | 확실한 악성만 자동 차단, 오탐률을 보고 임계값 조정 |
| 첫 요청 지연 (요청 시 동기 검증) | 검증 타임아웃, 동시 요청 시 검증 1회만, 공급망 결과는 버전별 캐시 |
| SBOM 생성이 느림(패키지 다운로드) | 타임아웃 초과 시 "정보 없음"으로 처리하고 뒤에서 채움 |
| MCPTox 라이선스 | 사용 전 확인, 안 되면 직접 만든 오염 샘플로 대체 |
| 게이트웨이 자체가 공격 대상 | 접속 인증, TLS, 레이트 리밋, 비밀값 분리 |

**게이트웨이 자체 보호**

글을 명령으로 읽는 것은 판별 LLM뿐이다. 파이썬 코드는 도구 설명을 문자열로만 다루므로, 인젝션 방어는 판별 LLM에 집중하고 실행 위험은 격리로 막는다.

| 위협 | 방어 |
| --- | --- |
| 설명으로 판별 LLM에게 정보 유출·행동 지시 ("이 서버를 털어라") | 판별 LLM에 도구를 주지 않음(파일·네트워크 접근 없음) / 프롬프트에 API 키·설정·환경변수를 넣지 않음 / 출력은 정해진 JSON(악성·의심·정상 + 근거)만 받고 그 외는 실행·표시하지 않음 |

**미결 사항**

- [ ] LLM 모델 선택
- [ ] 마감 일자 (9장 일정의 시작점)
- [ ] "공급망 정보 없음"을 부분신뢰(읽기만)로 둘지, 불이익 없이 기록만 할지
- [ ] 결정 테이블의 "고확신" 기준과 규칙 필터 패턴 목록
- [ ] DB·캐시를 SQLite·메모리 캐시로 축소할지 (7장)

**팀 설계와 다른 점**

| 항목 | 팀 보고서 | 개인 구현 | 이유 |
| --- | --- | --- | --- |
| 차단 시점 | 실행(호출) 시 통제 | 목록에서부터 제거 | 설명이 LLM에 들어가는 순간 공격이 성립 |
| 등급 합산 | 가중치·임계값 (미정) | 결정 테이블 | 판정 근거를 설명할 수 있어야 함 |
