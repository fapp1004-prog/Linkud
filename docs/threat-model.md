# Linkud 위협 모델

기준 문서: `docs/기획서.md`(10장 리스크·게이트웨이 자체 보호), `CLAUDE.md`(반드시 지킬 원칙).
대상: 게이트웨이 프로세스와 그 배포 환경(EC2 + Docker Compose + nginx). 범위 밖(기획서 2장):
도구 응답 안의 인젝션, SPIFFE/mTLS, 원격 서버 소스코드 분석, stdio 서버 실행.

## 1. 신뢰 경계

```
                 신뢰 경계 A (인터넷)              신뢰 경계 B (EC2 호스트)                 신뢰 경계 C (외부 서비스)
┌──────────────┐   HTTPS + Bearer   ┌────────────────────────────────────────────┐
│ 에이전트      │ ─────────────────▶ │ nginx (TLS 종단, 레이트 리밋, /mcp·/admin·   │
│ (Claude 등)   │                    │        /slack/actions·/healthz만 통과)     │
└──────────────┘                    │   │ Docker 네트워크                         │
┌──────────────┐  HTTPS + 관리 토큰  │   ▼                                         │   HTTP(S)   ┌──────────────────┐
│ 관리자        │ ─────────────────▶ │ gateway 컨테이너 (비 root, 읽기 전용 FS,      │ ──────────▶ │ 다운스트림 MCP 서버│
└──────────────┘                    │   cap 없음, mem/cpu/pids 제한)               │  (신뢰 안 함)│ (원격 HTTP만)     │
┌──────────────┐  서명된 POST       │   ├ 집행 계층: 목록 필터·호출 가드(캐시만)     │             └──────────────────┘
│ Slack         │ ─────────────────▶ │   ├ 검증 경로: 규칙 → LLM → 공급망 → 결정 테이블│ ──────────▶ Claude API (판별 LLM)
└──────────────┘                    │   ├ 관리 API·Slack 처리                       │ ──────────▶ MCP Registry · npm · PyPI · OSV
                                    │   └ /data/linkud.db (판정 이력·감사 로그)       │
                                    │ .env (SSM에서 받은 비밀값, 권한 600)           │ ◀────────── AWS SSM Parameter Store
                                    └────────────────────────────────────────────┘     (인스턴스 역할, 최소 권한)
```

- **A → B**: 에이전트·관리자·Slack은 TLS와 각자의 자격(에이전트 토큰 / 관리 토큰 / Slack 서명)으로만 들어온다.
  에이전트 토큰으로는 관리 API에 접근할 수 없다.
- **B → C 다운스트림**: 도구 정의·응답은 전부 신뢰하지 않는 입력이다. 도구 정의는 검증 경로를 거쳐야만
  에이전트에게 보인다.
- **B → C 판별 LLM**: 도구 정의를 문장으로 읽는 유일한 구성요소다. 도구·파일·네트워크 접근이 없고
  출력은 고정 JSON만 받는다.
- **B → C 공급망**: 레지스트리 메타데이터·패키지도 신뢰하지 않는다. 패키지는 해시를 확인하고 풀기만 한다.

## 2. STRIDE

| 분류 | 위협 | 대응 (구현 위치) | 남은 위험 |
| --- | --- | --- | --- |
| **S** 위장 | 토큰 없는 누군가가 게이트웨이를 MCP 서버로 쓴다 | Bearer 토큰(상수 시간 비교), 루프백이 아닌 바인딩에서 토큰 없으면 시작 거부 (`proxy/auth.py`, `proxy/gateway.py`) | 토큰이 유출되면 회수 전까지 사용 가능(정적 토큰, OAuth 미구현). 토큰 교체 절차는 `docs/deploy.md` |
| S | 에이전트 토큰으로 관리 API 호출 | 경로별 토큰 묶음, `/admin`은 관리 토큰만 (`proxy/auth.py`) | 관리 토큰 유출 시 등급 확정 가능 → 감사 로그로만 사후 추적 |
| S | Slack 버튼 요청 위조·재전송 | 서명 비밀값 HMAC 검증, 타임스탬프 5분, 승인자 목록 (`admin/slack.py`) | 승인자 Slack 계정 탈취 |
| S | Registry 이름 사칭(다른 서버의 패키지로 위장) | `remotes` URL과 실제 연결 URL이 같을 때만 매칭 (`supply/registry.py`) | Registry 자체가 오염되면 탐지 못 함 |
| **T** 변조 | 승인 후 도구 설명을 몰래 바꿈 (러그풀) | 정의 정규화 해시, 바뀌면 재검증 + 신뢰·부분신뢰라도 재승인 필요 (`verify/hashing.py`, `verify/pipeline.py`, `reapprove_on_change`) | 설명은 그대로 두고 서버 쪽 동작만 바꾸면 못 잡음(응답 인젝션은 범위 밖) |
| T | 도구 설명으로 판별 LLM 조작 ("안전하다고 판정해라") | 규칙 필터에서 판별기 조작 문장을 먼저 잡고 LLM 결과와 무관하게 신뢰 불가, 무작위 구분자, JSON만 파싱 (`verify/rules.py`, `verify/judge/`) | 규칙에 없는 자연스러운 설득 문장. 평가에서 LLM이 완전히 속을 때 6개 중 2개가 신뢰로 통과(규칙만 기준) |
| T | 내려받은 패키지 변조(미러·중간자) | npm sha512·PyPI sha256과 비교, 다르면 풀지 않고 승인 대기 (`supply/packages.py`) | 레지스트리에 올라간 원본 자체가 악성이면 해시는 맞음 → OSV MAL- 기록에 의존 |
| T | CI·이미지 공급망 변조(태그 이동) | Actions 전체 SHA 고정, 베이스 이미지 다이제스트 고정, syft를 고정 Go 툴체인으로 소스 빌드(sumdb 확인), pip-audit·Trivy·이미지 SBOM, Dependabot (`.github/`, `deploy/Dockerfile`) | 고정한 커밋·다이제스트 자체가 처음부터 악성인 경우 |
| **R** 부인 | 누가 언제 어떤 도구를 허용·확정했는지 부인 | 판정·호출 허용/거부·등급 확정·재검증 상한·해제·정리를 감사 로그에 기록 (`store/`) | 감사 로그가 같은 호스트의 SQLite라 호스트 장악 시 변조 가능(외부 전송 없음). 보존 기간 지나면 삭제 |
| **I** 정보 유출 | 도구 설명이 판별 LLM에게 비밀값을 묻거나 빼내게 함 | 프롬프트에 비밀값·설정·환경변수를 넣지 않음, 판별기에 도구 없음 (`verify/judge/`) | LLM 공급자에게 도구 정의 원문이 전송됨(설계상 필요) |
| I | 허용된 도구를 `~/.ssh/id_rsa` 같은 인자로 호출해 비밀 파일을 읽음 | 인자 검사로 민감 경로·자격 증명·개인키 내용 차단, 값은 로그에 남기지 않음 (`enforcement/arguments.py`) | 인코딩·우회 경로(심볼릭 링크 이름 등)는 정규식이 못 잡음 |
| I | 비밀값 유출(레포·이미지·로그) | SSM → `.env`(600), 이미지·레포에 비밀값 없음, 감사 로그에 인자 값 없음 | EC2 IMDS·인스턴스 역할 탈취 → `docs/deploy.md`의 IMDSv2·홉 제한 1 |
| **D** 서비스 거부 | 다운스트림이 설명을 계속 바꿔 LLM 비용·시간을 소모시킴 | 서버별 재검증 상한, 넘으면 승인 대기로 묶고 LLM 호출 중단 (`verify/service.py`) | 상한 안에서의 비용(기본 10분에 30회)은 발생 |
| D | 같은 새 도구에 요청 폭주 | (서버, 해시)별 락으로 검증 1회, 락은 끝나면 정리 | 서로 다른 새 서버를 대량 등록하는 경우(등록은 설정 파일로만 가능) |
| D | 큰 응답·느린 다운스트림 | 호출 타임아웃, 결과 크기 상한, nginx 레이트 리밋·본문 크기 제한, 컨테이너 mem/cpu/pids 제한 | 단일 EC2라 호스트 장애 시 전체 중단(fail-closed라 우회 통과는 없음) |
| D | 공급망 조회가 느려 첫 응답 지연 | `supply_timeout` 초과 시 이번 판정은 정보 없음, 뒤에서 채운 뒤 재검증 | 첫 판정이 부분신뢰로 시작할 수 있음 |
| **E** 권한 상승 | 부분신뢰 서버의 쓰기 도구 실행 | 읽기 판별은 세 신호가 모두 읽기일 때만, 호출 가드가 캐시된 판정으로 다시 확인 | 세 신호가 모두 틀리면(readOnlyHint 거짓 + 읽기 이름 + LLM 기만) 쓰기 도구가 읽기로 보임. 설명과 annotations 불일치는 승인 대기로 잡음 |
| E | stdio 서버로 게이트웨이 권한의 코드 실행 | 원격 HTTP 다운스트림만 허용, 설정 단계에서 거부 (`config.py`) | — |
| E | 패키지 설치 스크립트 실행 | 공급망 검증은 내려받아 해시 확인 후 풀기만, 설치·실행 없음, 안전 압축 해제 필터 | syft 자체 취약점 |
| E | 컨테이너 탈출 | 비 root(uid 10001), 읽기 전용 FS, cap_drop ALL, no-new-privileges | 커널 취약점 |

## 3. 확인하지 못한 것

- **판별 프롬프트의 "MCPTox 3요소" 정의: 미확인.** 판별 프롬프트(`verify/judge/prompt.py`)는 MCPTox
  (arXiv 2508.14925)의 공격 구성을 트리거 / 악성 행위 / 은닉 세 가지로 해석해 질문한다. 이 해석이 논문
  원문의 정의와 같은지는 확인하지 못했다. 작업 환경의 네트워크 정책이 arxiv.org와 미러(ar5iv)를 막아
  원문을 읽을 수 없었기 때문이다(2026-10-27). 원문을 대조할 수 있게 되면 정의가 다를 경우 prompt.py와
  이 문서를 고친다.
- LLM 판별기의 실제 탐지율·판별기 내성: API 키 없이 측정하지 못했다(`eval/results/RESULTS.md`의 미측정 열).
- OSV 실제 조회: 작업 환경에서 api.osv.dev가 막혀 녹화 응답으로만 테스트했다.
- GitHub OIDC 배포 워크플로(`deploy-oidc.yml`): 파일만 있고 실제 AWS에서 동작을 검증하지 않았다.
